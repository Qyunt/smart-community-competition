# 仿真验收、巡检耗时与检查点评估

验收日期：2026-10-08。环境：VMware Ubuntu 18.04、ROS Melodic、Gazebo 9；工作空间 `/home/qyunt/sq_community_ws_20261008`。

## 结论

项目能够在虚拟机中运行场景、采集传感器数据，并按固定里程计路线巡检。完成的一轮到达 33/33 个目标、保存 16 张任务照片，但发现第二处停止线的观察点设计有误：车身覆盖停止线时转向拍照，后来发生红灯期间移动。因此这轮只能证明目标点到达和抓图，不能判为完整交通规则验收通过。

已将 C 楼观察点从 `(0,-0.8)` 移到 `(0,-1.2)`，并禁止车身覆盖停止线时原地转向。修复后单独测试第二个路口的 4 个目标，全部成功，停止线覆盖采样均为绿灯。修复后的完整 33 点路线尚未重新整圈验收。

## 为什么慢

完成一轮各目标耗时合计 **905.5 秒，约 15.1 分钟墙钟时间**，包含暂停仿真排查的时间。第 9 个过路点记了 191.1 秒，包含排查暂停，不能当作正常走这一段的耗时。之前的失败重试、恢复起点及排查也增加了用户观看的总时间，不等于正常一圈半小时。

当前直行速度上限 `0.085 m/s`，转向上限 `0.38 rad/s`。转 90 度即使一直达到上限也要约 4.1 秒仿真时间，加上接近目标角度时的减速会更久。当前路径约 18.4 米，匀速直行的理论下限约 3.6 分钟仿真时间，还没有算转向、减速、拍照和等灯。

路线有 16 个任务目标与 17 个过路目标。现有 `drive()` 到每一个点都会停车，随后 `rotate()` 调整目标朝向。部分观察点需要面向目标拍照，再转回行驶方向，产生重复转向。两个路口又会等待完整的红转绿，以降低剩余绿灯时间不足的风险。这一轮两个信号目标分别耗时 34.1、50.9 秒墙钟时间，含驶近和等灯。

虚拟机使用软件渲染，检查前仿真实时因子约 0.81，巡检时观察到约 0.6～0.7。这个值会随负载变化：仿真 1 秒会花超过 1 秒的实际时间。

## 检查点是否合适

检查点现在是工程预设观察位，并没有全部通过视觉识别验收。定位误差小也不等于观察视角合适。完整一圈目标点平均平面误差约 2.38 厘米、最大 2.5 厘米，属于到点指标。

抽查了原 C 楼、新 C 楼、CAR_2、人群 A、表计照片：

| 检查点 | 实际观察 | 建议 |
|---|---|---|
| 第二处停止线 / C 楼 | 原位置车身压线，转向耗时期间变红；新位置转向时已离线 | 已修复交通几何；仍需复测整圈并核对所有窗户的可见性 |
| CAR_2 车牌 | 黄牌完整、居中，文字在照片里可读 | 此点可先保留；接入 OCR 后测试识别率。不能把肉眼可读视为 OCR 已完成 |
| 表计 | 两块表的数字完整可见 | 此点可先保留；还需实际算法结果和准确率 |
| PEOPLE_A | 前后人偶遮挡，右侧人偶被画面边缘裁切 | 增加侧向或分段观察视角，并跨视角去重。一个点不足以证明人数识别完成 |
| C 楼新视角 | 可见两处火焰纹理，但灯杆、车体及画面边缘仍影响覆盖 | 按楼栋、窗户建立覆盖表，必要时再补安全观察位或调整相机 |
| 其余点 | 本次已抓图，但未逐一验收算法和完整目标覆盖 | 逐项检查照片、目标大小、遮挡和识别结果，再决定保留或合并 |

## 红灯与停止线问题的证据

第一处路口：日志显示先识别绿灯再通行，到达线后目标约 7 秒后才变红。那张红灯截图中车辆已越过停止线，继续驶离路口本身不能判为闯红灯。

第二处路口：完整一圈额外采样发现 105 条“红灯、车身覆盖下方停止线、正在发运动指令”的记录，且位置和朝向也实际变化。这是明确的问题，不能用第一处路口的正确行为解释。采样条数不是独立违规次数。

局部复测从 BINS 点 `(0,0)` 初始化开始，按修复后的路线执行索引 18～21。该初始化是测试条件设置，不是完整比赛巡检的一段自主驾驶证据。控制器仍使用里程计、激光和相机；仿真灯态仅用于独立验收记录，没有送入巡检控制器。

复测完成 4/4 个目标、保存 2 张照片、道路采样 2561 条且越出道路采样 0 条。停止线覆盖采样共 73 条，全部绿灯，其中 64 条在发运动指令；没有红灯覆盖停止线移动记录。车身离线后才转向拍摄 C 楼。

## 已修复的代码

1. 上方红绿灯在当前场景的亮度约 114～120，原 145 阈值一直判 unknown。增加亮度 ROS 参数，将使用上方信号节点的 launch 阈值设为 90，保留颜色领先差值判断。
2. 原旋转超时用墙钟计时，低于实时运行时容易误超时。改为仿真时间期限，同时保留墙钟看门狗。
3. C 楼观察点改为 `(0,-1.2)`；同步任务点 CSV、场景生成器和 manifest，重新生成 33 点路线。
4. `sq_patrol_4p2.py` 根据车身尺寸与 16 毫米停止线厚度判断覆盖；覆盖时禁止有意义的原地转向，出错停车。
5. 修改前的文件均在虚拟机 acceptance 目录备份；修复后的场景静态检查和 Python 语法检查通过。

## 下一步优先做什么

先做路线与观察位优化，再做速度参数优化：

1. 将直线上的过路点改成连续通过，不再每 0.8 米停车；转角和任务点仍保留必要的减速与停车。
2. 合并重复转向。车辆支持全向平移，但是否可使用侧向行驶必须结合实际车体、感知方向和规则验证，不能直接用模拟器能横移作为实车依据。
3. 补齐人群和建筑的观察覆盖，接通 OCR / 检测，再按实际识别成功率调整距离与朝向。不要为了减少时间删除必要观察点。
4. 在独立测试中逐步尝试 `0.12～0.15 m/s` 直行、`0.6～0.8 rad/s` 转向，配套检查激光停止距离、转弯足迹、停止线离线时间和图像清晰度。这是待测参数范围，不是已安装或已验收的提速配置。
5. 完成修复和提速后，整圈重复验收，记录正常墙钟时间与仿真时间，排除暂停调试时间；持续检查碰撞、越界、停止线和任务结果。
6. 继续验收 SLAM / AMCL / move_base 的完整巡检，并接通人偶、火灾、车牌等识别。现在这轮固定里程计路线不能替代完整导航验收。
