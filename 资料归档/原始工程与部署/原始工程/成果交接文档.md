# 智慧社区复赛工程交接文档

更新日期：2026-10-08  
交接对象：已配置 ROS/Gazebo 环境、准备继续开发的队友

## 1. 这是什么

这是智慧社区比赛的 ROS1/Gazebo 源码工作空间。压缩包根目录直接包含 `src/` 和本交接文档；`src/` 中有 `sq_community` 主包及随包提供的 `turtlebot3*` catkin 源码依赖。工程按 Ubuntu 18.04 + ROS Melodic + Gazebo 9 编写。包中不含构建产物，解压后需要在队友自己的工作空间编译。

本包不是最终竞赛全套交付物：不包含技术方案 PDF、答辩展示 PDF 或综合展示视频；队名也尚未确认，所以文件名中的 `【队名】` 是占位符。

## 2. 从解压到启动

如果队友已有 `~/sq_ws`，先备份或选择新的工作空间目录，避免覆盖自己的 `src/`。将本包解压后，在包根目录运行：

```bash
cd <解压后的工程包目录>
catkin_make
source devel/setup.bash
```

首次检查当前 4.2 m 场景：

```bash
roslaunch sq_community sq_community_4p2.launch
```

无桌面显示时：

```bash
roslaunch sq_community sq_community_4p2.launch gui:=false
```

停止 Gazebo 后，可先跑不启动仿真的静态检查：

```bash
cd src/sq_community
python3 tools/verify_scene_4p2.py
python3 tools/verify_map_4p2.py
python3 tools/verify_props_3d.py
```

脚本和参数若依赖工作空间包路径，请在已 source 的终端运行。具体依赖以 `src/*/package.xml` 和相关 launch 文件为准。编译/运行前建议复制一份工作空间或使用版本控制分支。

## 3. 先看哪些文件

1. `README.md`：开发包入口与工程边界。
2. `src/sq_community/SCENE_4P2_README.md`：当前 4.2 m 场景说明、launch 与组件状态。
3. `src/sq_community/tools/`：场地生成器、真值清单、路线和地图生成/验证工具。
4. `src/sq_community/launch/`、`param/`、`config/`、`urdf/`：仿真、导航、传感器和机器人配置。
5. `src/sq_community/docs/人物立牌纠正验收_20261002.md`：人偶几何修正与视觉验收边界。

工程中当前 4.2 m 相关入口包括：

- 场地：`worlds/sq_community_4p2.world`
- 主仿真：`launch/sq_community_4p2.launch`
- 导航/自主巡检相关 launch：文件名带 `4p2` 的版本
- 静态地图：`maps/sq_community_4p2.pgm` + `.yaml`，性质是几何先验，不等同于已验收的 SLAM 地图
- 场景真值：`docs/scene_manifest_4p2.json`
- 巡检路线：`route/sq_route_patrol_4p2.csv`

旧的 `sq_community.world`、旧地图/旧航线与不带 `4p2` 的部分 launch 仍保留作历史参考。它们属于早期 10.0 m × 7.2 m 基线，不能与 4.2 m 场景混用。

## 4. 当前进度：哪些能信，哪些还不能

依据现有源码文档和静态验证 JSON（本轮未在队友环境重新运行）：

- 4.2 m world、模型、独立 launch、地图/路线文件和生成/验证工具已在包内。
- `docs/props_3d_validation.json` 记录几何检查通过：18 个立牌（16 个居民参考、2 个非居民参考）及电动车模型几何检查。它只验证模型和布置几何，不等于识别准确率验收。
- 工程说明称曾执行 33 个目标点的里程计/LiDAR 路线；本包没有随附完整 VM 运行原始报告和关键帧，因此接手者应复核原始证据，不能只把 README 描述当作当前设备上的通过记录。
- OCR 对已知的三张车牌巡检图有过集成冒烟测试记录；这不证明对未知车牌的泛化。运行 OCR 服务还依赖工作空间外的 Python 3 服务/库。
- 人群/火灾 YOLO 识别、跨画面人数去重、非居民识别播报尚未闭环；14 个建议相机视角也未集成进巡检。
- SLAM 与 move_base 的 4.2 m 全程路线需要在已配置环境中单独验收。不要把里程计路线完成等同于 move_base 全程通过。

## 5. 接手前必须先核对的结构问题

此前项目检查已指出：规则图中的道路规划与已有地图表达存在不一致疑问，并提出地图缺少一个人群区。当前源码包没有可证明该问题已闭环的记录；因此在改导航参数或认定地图最终版之前，先做规则图 → `scene_manifest_4p2.json` → `sq_community_4p2.world` 的逐区核对，重点列出 A/B 街、建筑、停车区、任务区、人群区、人行横道、信号灯和蓝色行驶方向。不要凭视觉感觉补精确坐标；无尺寸依据的坐标应标为比例估计/待确认。

项目另有独立的 `map_analysis/community_map.yaml` 与 21×21 SVG 分析稿，但它们不在本源码 ZIP 中，也未与当前 world/manifest 完成逐项合并核对。不要直接用分析稿覆盖工程场景。

另一个已知尺寸差异：当前 4.2 m 机器人 URDF 外廓说明约为 334 × 303 mm，而比赛参数确认的机器人外廓为 400 × 400 mm。该差异会影响道路净空、足迹和导航代价地图，应由团队先决定并记录，再进行路线验收。

## 6. 导航与运行安全提示

- `sq_patrol_4p2.py` 与 `sq_patrol_nav_4p2.py` 都会控制 `/cmd_vel`，不可同时启动。
- 建图时不要同时启动 AMCL/map_server；保存 SLAM 图后，再单独使用导航 launch。
- `sq_community_4p2.launch` 默认打开 Gazebo GUI；无头环境传 `gui:=false`。
- 场景模型纹理依赖 `GAZEBO_MODEL_PATH`。主 launch 已配置该路径；若另行手动启动 `gzclient`，按 `SCENE_4P2_README.md` 设置环境变量。
- 老场景地图、旧坐标、旧 23/25 点路线不得与 4.2 m 路线混用。

## 7. 建议接手顺序

1. 在自己的分支/副本编译，保存完整退出码和依赖缺失信息。
2. 单独启动 `sq_community_4p2.launch`，确认 world、机器人、传感器话题和信号灯。
3. 先完成规则图与 world/manifest 的结构差异表，解决道路/人群区问题和 400 mm 机器人外廓决策。
4. 结构冻结后再验证地图净空、SLAM、AMCL/move_base 路线；每次运行保存日志摘要、地图、路线指标和关键帧。
5. 最后补 YOLO 人群/火灾识别及完整任务演示验收；报告区分几何自检、集成测试和真实识别效果。

## 8. 出问题先查这里

- 找不到 ROS 包：确认 `catkin_make` 成功且当前终端已 `source devel/setup.bash`。
- Gazebo 模型灰白/缺失：检查 `GAZEBO_MODEL_PATH` 是否包含 `src/sq_community/models`。
- Gazebo GUI 不出现：按 `SCENE_4P2_README.md` 检查 `gzserver/gzclient` 启动次序；无头启动可先用 `gui:=false`。
- 机器人不动/路线卡住：确认没有第二个巡检节点同时写 `/cmd_vel`，并核对 topic、TF、`/scan`、`/odom`、足迹和地图版本。
- 视觉节点无结果：区分 ROS 桥接节点与外部 Python 3 OCR/YOLO worker；检查 worker 是否启动、网络地址/端口是否可达。源码存在不代表外部模型服务已部署。

## 9. 本包验证范围

ZIP 已在打包设备上解压核对，根目录应为 `README.md`、`成果交接文档.md`、`src/`。关键 4.2 m world、launch、地图、真值和路线文件在包内。打包设备没有 `catkin_make`，所以没有执行编译，也没有在 Gazebo 中重跑实验；请队友将自己的编译/仿真结果补入团队验收记录。桌面原工程未被修改。
