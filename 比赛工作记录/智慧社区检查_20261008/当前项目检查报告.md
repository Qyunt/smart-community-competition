## 代码检查发现的具体问题

### 1. 仿真变慢会压缩巡检的运动超时预算

`scripts/sq_patrol_4p2.py` 的转向、移动、判灯等待，以及 `sq_patrol_nav_4p2.py` 的目标超时，均以 `time.time()` 计算现实时间；部分图像新鲜度判断又使用 `rospy.Time.now()` 的仿真时间。

例如转向允许 18 秒现实时间，当前速度约 0.684 时，仿真只推进约 12.3 秒。更严重的渲染卡顿会让机器人还没完成合理动作就触发超时。两套巡检对视觉结果的新鲜度又用约 0.7 秒现实时间判断，而视觉节点的 Timer 按仿真时间运行，低实时系数时可能把有效结果当作过期。

本次没有实际触发这个失败，判断依据为计时实现与实时系数。建议让运动/红绿灯阶段按仿真时间计时，同时保留独立的现实时间看门狗处理暂停或失联；HTTP 网络请求继续使用现实时间超时。不能简单把所有计时都换成仿真时间。

### 2. 不能直接缩小相机分辨率来解决卡顿

`sq_signal_vision_4p2.py` 对非 720×1280 图像直接返回 `unknown`，红绿灯 ROI 使用固定像素坐标。`tools/plate_ocr_4p2.py` 同样要求 1280×720，并固定了车牌裁剪位置。

如果将相机改成 640×480，而没有修改 ROI 与尺寸检查，会破坏现有识别。建议先评估 GUI、纹理和不需要的传感器输出；若要改分辨率，需同时按尺寸缩放 ROI 或重新标定，随后回归两处信号灯与三处车牌视角。

### 3. 任务相机观察质量需要现场验证

任务相机安装在车体后部约 `(-0.120,0.065,0.140)` 米，却朝向前方。当前任务相机截图能看到较大的近处车体部分，画面下部被占据。不能只看模型尺寸与相机有消息就宣称任务都可看清。

需要在 16 个任务点逐个保存前/任务相机图，检查任务对象是否完整、文字够清晰、有无遮挡；把包内 14 个建议观察姿态与真正可自主到达的路线对齐。

### 4. YOLO 示例不能直接作为 Melodic 检测部署方案

`sq_vision_demo.py` 的 ROS 节点直接尝试导入现代 Ultralytics，但当前 ROS 使用 Python 2。源码包没有模型权重，默认也只抓图。建议参照已有 OCR 架构，将 Python 3 推理服务与 ROS 端拆开，并把 `/sq/patrol/observation` 接入模型结果、存图和语音。

此外，该示例发布 `/sq/vision/result`，现有语音节点订阅 `/sq/voice/say`；即使示例产生检测结果，也需要明确的转换/转发流程才会自动播报。

### 5. 打包安装配置还不完整

`CMakeLists.txt` 的安装目录列表没有 `urdf/` 与 `config/`，而当前 launch 使用机器人 URDF。现在使用源码工作空间和 `devel/setup.bash` 能运行，但未来执行 `catkin_make install` 后会漏掉这些资源，需要补齐。

`package.xml` 仍描述旧 10×7.2 米场景，且没有明确声明当前 launch 使用的 `xacro`、视觉示例使用的 `std_srvs` 等依赖。应与实际入口和导入列表核对，以便别人从干净环境复现。

这些问题尚未修改；本次任务为检查，原工程和当前仿真保留。
